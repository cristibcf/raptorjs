# Round 3 — `@raptor/ui` and the compilation pillar

The first two rounds touched the component library (18,000
lines) and the `compiler` → `engine` chain only superficially. This round went there.

**7 findings, all closed.** Three of them make the compiler emit code
that **throws at runtime** or that **computes something other than what the source says** —
that is, exactly the central claim of the compilation pillar.

## U4 — DSE deletes a `derived` read in a handler → code that throws — **High**

```
component App {
  const count = state(0)
  const pas = derived(() => 10)
  <button on:click={count += pas}>+</button>
}
```

`raptor build` reports success ("eliminate 1") and emits:

```js
export function App() {
  const count = state(0);
  applyProps(_e1, { "on:click": () => count.set((count() + pas)) });
  //                                                        ^^^ undeclared
}
```

`ReferenceError` on the first click, from a green build.

**The cause**, in `compiler/src/graph.ts`: the event node received edges only from
`ev.writes`, never from `ev.reads`, and had `sink: false`. A handler therefore
kept nothing alive, and the reverse reachability from sinks never reached
`pas`.

## U5 — DSE deletes a signal written only in a handler — **High**

The same root, the other end:

```
component App {
  const vizite = state(0)
  <div><button on:click={vizite++}>count</button><span>static</span></div>
}
```

`vizite` disappears from the declarations, and the handler remains `() => vizite`. A
counter that you only increment is a perfectly normal state.

**Fixed (U4+U5):** the event node is `sink: true` — a handler *is* an
observable output — it receives read edges like any binding, and liveness
also tracks the written targets: the code emitted for a live handler **names** them,
so deleting them leaves a dead reference in the file. After the fix, `pas` is
actually fused into the handler (`count() + 10`), which is even better.

## U1 — Dependency Fusion captures variables — **High**

```
const x = state(1)
const a = derived(() => x + 1)             // `x` = the signal
const b = derived(() => items.map(x => a)) // `x` = map's parameter
```

The fusion produced `items.map((x) => (x + 1))`: `x` is no longer the signal, but the
parameter. **A different program.** And on top of that the dependency list became `[x]`,
so the binding subscribed to a signal that the emitted code did not even read anymore.

`substituteIdent` correctly handled the shadowing *of the replaced name*, but not the capture
of the free identifiers *of the replacement*.

**Fixed.** The signature now returns `Expr | null` — `null` means "would
capture" — deliberately: a caller cannot forget the case, because it has
to handle it in order to compile. The fusion halts and writes why in the trace.

## U2 — Fusion duplicates work — **Medium**

The condition was "a single consumer". But a single consumer does not mean a
single **use**: `derived(() => n*n*n)` used as `scump + scump` became
`(n*n*n) + (n*n*n)`, with the memo deleted. An "optimization" that slows things down, silently.

**Fixed:** free uses are counted; above one, the fusion halts.

## U3 — a `derived` that writes compiled silently — **Low**

`derived(() => n++)` was accepted, and `exprToJs` ignores writes in read
position (codegen emits them separately) — so the increment **disappeared** from the emitted code.
**Fixed** by refusing at parse time, with a message that says where the write belongs.

## `@raptor/ui`

## U6 — 11 components re-rendered the region that builds them — **Medium**

A component that reads a signal *while it is building* subscribes the caller's
computation to that signal. If the caller is a reactive binding — a
`Show`, a `For`, any real region — the first interaction rebuilds the entire
region. It is not just waste: the rebuilt region loses node identity,
so **focus, scroll, and whatever was typed in an input**.

Measured on the site catalog, mounting each demo in an `effect` and pressing
the first button in it: **11 of 93** interactive components re-ran the parent —
`Select`, `ColorPicker`, `TreeSelect`, `Cascader`, `DatePicker`,
`DateRangePicker`, `Menubar`, `Popover`, `DropdownMenu`, `Tour`, `Transition`.

The site worked around the problem with `untracked(() => c.demo())`. **A workaround written in
the consumer is the sign that the problem is in the library**: anyone using
`@raptor/ui` in a binding hits it without knowing why.

**Fixed** in the library (`primitives/isolate.ts`), applied to the 11.
The workaround was removed from the site — if a component starts leaking again, the catalog
test sees it. Re-measured: **11 → 0**. Verified in a real browser too: the menu
opens, with no console errors.

## U7 — `javascript:` passed through unfiltered in `href` — **Medium**

`Link({ href })`, `Breadcrumbs`, `SidebarNav`, `NavigationMenu` take the address from
props and pass it on to `setAttribute`. Verified: `javascript:alert(1)`
ends up in the DOM as an executable link.

It matters more here than in an ordinary framework: the RaptorWire thesis is that
state comes off the wire and is applied locally, so **a navigation element sent
by the server is the expected case**, not an exotic one.

**Fixed in the DOM runtime**, not in `@raptor/ui`: an application that writes JSX
directly has the same hole too. The filter covers `href`, `src`, `action`, `formaction`,
`poster`, `srcdoc`, `data` and `xlink:href`, normalizes the spaces and control
characters before the scheme (`" java\nscript:"` is still executable for the
browser), catches `vbscript:` and `data:text/html`, applies **on binding update too**,
not just on mount, and leaves ordinary addresses untouched,
including `data:image/...`.

## What we checked and what held up

- **DSE remains useful**: a truly dead derived is still eliminated.
- **Fusion remains useful**: a consumer with a single use is fused.
- **`analyze`** correctly handles shadowing: an arrow parameter named
  like a signal does not produce a false dependency.
- **The expression parser** does not confuse long chains with deep nesting.
- **The rest of the catalog**: 211 demos render, 0 parent re-renders.

## What remains open

`@raptor/ui` has 18,000 lines and a 0.26 test ratio. We checked two axes
— reactive leakage and injection through `href` — on all components. We did **not**
check: per-component ARIA correctness, cleanup of global listeners
beyond the few we read, and the keyboard behavior of each
composed component. These are claims the library makes and that this round
did not test.

# Round 2 — re-audit after fixes

The second pass, with emphasis on **the code written in the first**: the fixes are the newest
and least reviewed part of the repo, and a fix is a claim — claims are audited in
turn.

Out came **5 security findings** (one that almost completely undoes a
fix from the first round) and **7 quality ones**. Ten were closed, two
remain open and are named as such.

## R1 — the anti-bypass gate is evaded with a computed `import()` — **High**

The first round closed the *visible* bypass: an `import` of `node:fs` that the static
graph sees (S5). But the graph does not see a computed specifier:

```js
const nume = ["node", "fs"].join(":");
const fs = await import(nume);      // nothing reaches `hostImports`
```

**PoC run**, empty manifest, `policy: "production"`:

```
evasiv@0.0.1 ran (production policy, strict)
  capabilities denied  0
exit=0
```

The application read `C:/Windows/win.ini` and the runtime reported zero refusals.
The irony: `doctor` **flagged** the computed import as an error — `run` did not look
at `graph.unresolved` at all. Exactly the shape of S5, moved one row over.

**Fixed.** The contract in `bypass.ts` is no longer "the list of bypasses", but *what I know*
and *what I cannot know*. An unresolvable import is not proof that everything is fine; it
is the absence of a proof, and in strict mode the absence of proof is not enough. Under
`production` it stops startup, under `development` it appears in the summary and in the audit.

## R2 — `findBypasses(...).catch(() => [])` was fail-open — **Medium**

If the static graph could not be built — an import that does not resolve, an
unreadable file — `catch` returned an empty list and `run` started the application in
production **without any check**. "I found nothing" and "I couldn't
look" are different things, and the code confused them in the dangerous direction.

**Fixed.** `inspectBypasses` also returns `graphError`, and in production it is
a reason to refuse like any other. Verified: a project with a missing import is now
stopped, not started.

## R3 — the list of variables that load code was incomplete — **Medium**

S1 introduced a blocklist for `NODE_OPTIONS`, `LD_*`, `BASH_ENV` and others,
with a comment saying it was "a deliberately inverted allowlist, so a new variant
does not pass". **False.** With `env.read: ["*"]` granted, all of them passed:

```
NODE_PATH          ACCEPTED        RUBYOPT       ACCEPTED
JAVA_TOOL_OPTIONS  ACCEPTED        PYTHONHOME    ACCEPTED
_JAVA_OPTIONS      ACCEPTED        CLASSPATH     ACCEPTED
```

Every ecosystem has its own variables that load code, and others keep appearing.

**Fixed by changing the model, not just the list.** Reading and writing are not
the same thing: the **`env.set`** capability appeared, separate from `env.read`,
empty by default. The child inherits the environment filtered through `env.read`; whatever
the application wants to add on top must be declared by name. The blocklist remains as a
second stage (and is much longer), but the boundary is now `env.set` — and the
comment states clearly that the list is **not** the boundary.

## R4 — credentials carried over to the next host after a redirect — **Medium**

S2 put `broker.require` on every hop, but the loop carried `init` forward
untouched — so `Authorization` and `Cookie` reached the destination host:

```
the second host received authorization: Bearer SECRET-TOKEN
the second host received cookie:        sid=abc
```

Both hosts were declared, so the capability model was not violated —
but a token for `api.example.com` has no business at `cdn.example.com` just
because the first responded 302. Browsers cut them off exactly here.

**Fixed.** On a hop to another destination, `Authorization`, `Cookie` and
`Proxy-Authorization` are removed, the rest of the headers go forward, and the
event enters the observer. A bonus found while fixing: when `input` was a
`Request`, *all* of its headers were lost after the first hop — they are now
merged before the loop.

## R5 — recursive `sanitize`, without a limit — **Low**

The recursive cleaning added for S9 fell over with `RangeError: Maximum call stack
size exceeded` at around 5,000 levels, whereas V8's `JSON.parse` handles
50,000 without blinking.

**Verified before inflating the severity:** both places that call
`decodeFrame` have it in a `try/catch`, so the frame is rejected and the host does not crash.
So it is not a DoS — it is a poor message: "stack full" suggests that something broke
on our side, when in fact the limit is a choice that nobody had made.

**Fixed.** An explicit limit of 64 levels, with `raptor:host/protocol` and a
message that says what happened.

## Quality

**R6 — flaky test. Medium.** `run/dev-server`, the SSE broadcast test, failed ~1 in
4 runs of the full suite and passed 5/5 in isolation. The cause: `setTimeout(60)` to
"let" the SSE client register in time — an assumption about how loaded the
machine is, which fails exactly in CI. **Fixed** by waiting for the *condition*
(`hmrClientCount > 0`), not a duration; the `fs.watch` test rewrites the file until
the event actually arrives. Verified: 5 consecutive full runs, 0
failures.

**R7 — `pnpm stats` published numbers from a red suite. Medium.** The tool read
`fail` and ignored it: it wrote "N tests (M pass)" in the README and exited 0. A number
measured on a red suite is worse than a hand-written one, because it looks
measured. **Fixed**: it refuses and says what to run.

**R8 — the `.raptor` parser gave `RangeError` on pathological nesting. Low.**
Recursive-descent without a depth limit. The rest of the fuzzing came out clean:
10 malformed inputs, all with `RaptorParseError` with position, no hangs.
**Fixed** with explicit limits (256) in both parsers.

**R9 — `@raptor/test` is the least tested package. Low, OPEN.** 97 lines
of test for 1,076 lines of source, a ratio of 0.09 — the weakest in the
repo, in the verification pillar itself. `chaos`, `network`, `oracle`, `probe`,
`raptor-test` and `replay` have no tests at all. Not fixed: it is the work of writing tests, not
a hole to close. Marked on the site, where the row said "Ready".

**R10 — `parseCapsule` validates two fields. Low, OPEN.** The
`.raptorcap` format is designed as a *shareable* artifact — you receive it from someone else's
report and run it — and it is validated with `Array.isArray(actionLog) &&
networkSchedule`, then cast. Verified that `VirtualDB.update` is prototype-safe,
so it does not lead to pollution; what remains is thin validation without tests.

**R11 — a documentation row left behind after my own edits.**
The "What's ready" lesson still said "three findings, all fixed" and marked

**R12 — the Rust numbers are not covered by `pnpm stats`.** The README claimed "151 Rust
tests" (there were 154). The binary sizes are correct, though — verified:

## 1. Security — new findings

Every finding below has a proof-of-concept that was run, not an assumption.
The severity is measured against the project's thesis: *"security is a function of
the product, not an optional wrapper"* (`packages/runtime/src/capabilities.ts:2`).

### S1 — `process.spawn`: the environment and `cwd` do not pass through the broker → complete escape — **High**

**Where:** `packages/runtime/src/modules/process.ts:56-77`

The broker checks **the command name**, then the code does:

```ts
// The child's environment contains only the variables the application can read.
for (const key of this.envKeys()) { ... }
Object.assign(childEnv, options.env ?? {});   // ← undoes the line above
...
spawn(command, [...], { cwd: options.cwd ?? host.projectRoot, env: childEnv })
```

`options.env` overwrites the filtered environment, and `options.cwd` is not checked
at all. The comment above describes a property that the code below it
undoes.

**PoC run** — manifest with a single capability, `process.spawn: ["node"]`,
zero `env.read`, zero `files.*`:

```
envKeys visible to the application: 0
reading PATH: raptor:capability/undeclared
stdout: "ARBITRARY CODE executed from NODE_OPTIONS, cwd = C:\Windows"
```

The application cannot even read `PATH` through the broker, but it sets
`NODE_OPTIONS=--require <payload>` for the child and runs arbitrary code, with the
working directory outside the project. On Linux, `LD_PRELOAD` does the same
thing for any binary, not just for `node`. A capability that promises
"*which* commands" becomes "any code".

**Fix:** filter `options.env` through the same rule as `envKeys()` (or
require a separate capability for each key set), put `cwd` under
`files.read`/`files.write` via `containsPath`, and explicitly block the
code-loading variables (`NODE_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`,
`DYLD_*`, `BASH_ENV`, `GIT_SSH_COMMAND`).

### S2 — `net.fetch` does not re-verify the destination after a redirect → SSRF — **High**

**Where:** `packages/runtime/src/modules/net.ts:48-72`

`host.broker.require("net.connect", destination)` runs only once, on the
initial URL. `fetch()` defaults to `redirect: "follow"`, so the next hop
no longer sees the broker.

**PoC run** — manifest with `net.connect: ["127.0.0.1:9200"]`:

```
allows 9200 (allowed): true
allows 9201 (internal): false
fetch to 9200 -> status 200 | final URL: http://127.0.0.1:9201/ | body: "SECRET-METADATA-TOKEN"
```

The application read the contents of a host that the broker explicitly refuses.
In the cloud, the equivalent target is `169.254.169.254`.

**Fix:** `redirect: "manual"` in `init`, an own follow loop with
`broker.require` on every hop and a hop limit. An explicit refusal
of `options.redirect` coming from the caller is also worthwhile.

> For contrast: the HTTP client in the native runtime
> (`crates/raptor-runtime-core/src/http.rs`) **does not follow redirects at all**,
> so it is correct by construction. The divergence is in Rust's favor.

### S3 — the RaptorBundle dev-server: prefix without a delimiter + bind on all interfaces — **Medium**

**Where:** `packages/bundle/src/dev-server.ts:98-99` and `:148`

```ts
const filePath = join(root, url);
if (filePath.startsWith(root) && ...)      // prefix without a boundary
...
server.listen(port, () => { ... })          // no host → 0.0.0.0 / ::
```

This is exactly the class of bug fixed as finding #2 in the previous audit
(`server/store.ts`), reintroduced here.

**PoC run** (raw socket, because `fetch` normalizes the path):

```
GET /../app-privat/.env  ->  HTTP/1.1 200 OK  |  "SECRET_TOKEN=abc123"
```

The reachable scope is bounded to paths that have `root` as a string prefix
(`site` → `site-backup`, `site.old`), but inside the root there is no
hidden-file filter: `GET /.env` serves the project's secrets. With
`listen` on all interfaces, it is accessible from the LAN.

The second effect, functional: the path is never decoded, so an asset with
`%20` in its name gives 404.

**Fix:** `decodeURIComponent` on the path, then `containsPath(root, filePath)`
(the helper already exists in `packages/runtime/src/paths.ts`), refusal on segments
that start with `.`, and `server.listen(port, "127.0.0.1")` with explicit opt-in
for exposure.

> `@raptor/run`'s dev-server (`packages/run/src/dev-server.ts:153`) correctly binds
> on `127.0.0.1` and does not serve arbitrary files. Only the one in `bundle` is affected.

### S4 — `serve` opens ports without any capability — **Medium**

**Where:** `packages/runtime/src/modules/serve.ts` (no broker call in the entire
file) and `crates/raptor-runtime-core/src/modules.rs:376`
(`fn serve_module(observer: Observer)` — does not receive a broker).

The runtime's capability vocabulary
(`packages/runtime/src/manifest.ts:13`) does not even contain `net.listen`. An application
with an empty manifest can bind a port; in the native variant it can also pass
`hostname: "0.0.0.0"`.

The contradiction is internal: `@raptor/host` **requires** a capability for exactly the same
methods — `packages/host/src/protocol.ts:121-125` maps
`serve.listen`/`respond`/`stop`/`status` → `net.listen`. The two layers do not
agree on who decides.

**Fix:** add `net.listen` to `CAPABILITY_KINDS`, with the target
`host:port` matched by `matchHost` (which already exists), and pass the broker into
`serve_module`.

### S5 — the broker is bypassable on the bootstrap engine; `doctor` says so, `run` does not — **Medium**

**Where:** `packages/runtime/src/engine-adapter.ts:170-178` — the `node:` imports
are **classified and recorded**, not blocked.

**PoC run** — project with `policy: "production"`, `capabilities: {}`:

```
$ raptor-runtime run
evil@0.0.1 ran (production policy, strict)
  capabilities denied  1
```

The program requested `files.readText("C:/Windows/win.ini")` → correctly refused; then it
did `await import("node:fs")` and read the same file. `run` reported success.

The good part: `raptor-runtime doctor` **catches** this —
`packages/runtime-cli/src/commands/doctor.ts:111` emits
*"node:fs bypasses the capability broker"*. The problem is that the warning lives
only in `doctor`, and `.raptor/audit.jsonl` contains **only the refusal**, not the
successful read via the other path. An audit log that shows "1 capability
denied" for a file that was read anyway misleads exactly the
person reading it to decide.

**Fix (minimal, does not require real isolation):** run the check from `doctor`
in `run` too; under `policy: "production"` turn it into an error, under `development`
write it into `audit.jsonl` as a `bypass`-type record. And state in
`engine-adapter.ts` in big letters that on bootstrap the broker is **advisory** —
today it only says there that "isolation belongs to the native host", which is not the same
thing as "it can be bypassed here".

### S6 — path containment is purely lexical (symlink) — **Medium**

`packages/runtime/src/paths.ts` resolves with `resolve()`, without `realpath`. A
symlink located in the granted scope takes the read/write outside of it.

The native runtime has the **same** limitation, but **documents** it explicitly
(`crates/.../paths.rs:13`: *"normalization does not follow symlinks"*). The
TS side does not mention it, and it does not appear in "Known limitations" in the old audit.

**Fix:** either `realpath` on the parent directory before the comparison (with
TOCTOU care), or — cheaper and more honest — a line in the docs and in the file comment,
on both sides.

### S7 — WebSocket: no `Origin` verification, no connection quota — **Low-Medium**

**Where:** `packages/server/src/websocket.ts:192-206`

The handshake checks only the path and the presence of `sec-websocket-key`. It does not look at
`Origin`, so any page the user opens can open a
connection to a Raptor server (`ws://localhost:...` or a production one, with
its cookies) — cross-site WebSocket hijacking. There is neither a limit on
simultaneous connections nor a handshake timeout.

The rest of the RFC 6455 parser is solid and worth stating: mandatory mask
(`:164`), `MAX_FRAME_BYTES` and `MAX_MESSAGE_BYTES` at 16 MB, unknown opcode →
close, `teardown` that removes the connection from the store.

**Fix:** a list of allowed origins in `WebSocketOptions` (default: only
same-origin), plus `maxConnections`.

### S8 — `spawn`: unbounded buffers, stop without escalation — **Low**

`stdout`/`stderr` accumulate in strings without a cap
(`modules/process.ts:78-84`): a talkative child exhausts the runtime's memory.
On `abort`, `child.kill()` (SIGTERM) is sent without escalation to SIGKILL, so
a child that ignores the signal survives the deadline.

The previous audit claims "unbounded loops: all have a bound" — here that is not the case.

### S9 — `plain()` is shallow (hardening) — **Low**

`packages/host/src/protocol.ts:151-163` cleans `__proto__`/`constructor`/
`prototype` only at the **first level**. `JSON.parse` produces `__proto__` as an
own property, so an `Object.assign({}, frame.params.ceva)` done by a
consumer further down would trigger the setter. There is no such consumer today; it
is worth recursion anyway, because the file titles itself *"nothing from the
frame can touch the prototype"*.

### S10 — `@raptor/wire-client` has no tests at all — **Low**

The only two packages without a `tests/` directory are `runtime-native` (it has inline Rust
tests, so it is fine) and **`wire-client`** — exactly the component that
ingests hostile bytes from the network and applies operations to the local state.

A direct consequence: finding #3 from the previous audit (the client fail-closed on
corrupt frames) is the only one of the three **without a regression test**. It can
disappear in a refactor without anything failing.

## 2. What we checked and is fine

Worth stating explicitly, so the fixes do not touch what works:

- **Zero runtime dependencies — confirmed.** No Vite/esbuild reference in the lock;
  `benchmarks/` and `integrations/rolldown/` have their own `node_modules`, outside the
  workspace.
- **Zero TODO/FIXME/HACK debt** across all `packages/*/src` and `examples/*/src`.
- **The RFC 6455 parser** (except `Origin`): mandatory mask, caps on the
  frame and on the reassembled message, no quadratic copying.
- **The host bridge** (`packages/host/src/protocol.ts`): prototype-safe JSON
  decoding, `hasOwnProperty` on method lookup, a capability declared
  explicitly per method.
- **The capability broker**, as logic: `matchHost` is not fooled by

- **The fixes from the previous audit are still in place:** `setOwn` in

- **`CodeEditor`** receives `highlight` which returns `Child` (nodes), not HTML —

- **The benchmark numbers are honestly sourced**: the bars on the home page

## 3. Documentation — divergences from the code

### D1 — `pnpm typecheck` does not pass, but the README presents it as passing — **High**

README.md:22 lists `pnpm typecheck  # tsc --noEmit pe tot` among the commands
that work. The reality: **7 errors, exit 2**, all in the two native examples:

```
examples/native-hello/src/main.ts(21,7):  Type 'Promise<string>' is not assignable to type 'string'.
examples/native-server/src/main.ts(58,22): Property 'listen' does not exist on type 'RaptorServe'.
  ... (respond / next / close)
```

The cause is not a typo, but a **real contract divergence**: the native
binary exposes `raptor:files` and `raptor:serve` **synchronously**
(`serve.listen/next/respond/close`), whereas the ambient declarations in
`packages/runtime/src/raptor-modules.d.ts` describe the **asynchronous** surface of the
TS runtime (`serve.serve()`, `files.readText(): Promise<string>`).

The useful irony: that file writes in its header that *"the types come from the real
contracts of the host, so they cannot fall behind the implementation"*. Exactly
that is what happened. There are two `raptor:` surfaces, not one, and the `.d.ts`
describes only the first.

**Fix:** declare the two profiles explicitly (e.g.
`raptor:serve` async for bootstrap and `raptor:serve/sync` for native, or a
discriminated union on the profile), and put `pnpm typecheck` in CI as a guard.

### D2 — `SECURITY-AUDIT.md` is out of date in misleading ways — **High**

The document (Sept 21) asserts, as the current state:

| Claim | State on Sept 24 |

| "Verification: **75/75 tests**" | 804 tests |

| "Scope: the packages and examples written in this session" | covered ~10 packages; today there are 24 + a Rust runtime of ~8,000 lines |

The claim about `fs`/network was true when only `core`, `dom` and
`wire-*` existed. Today it is false, and it is repeated publicly on the site (see C1).

### D3 — There is no LICENSE file, although 23 packages + README + site say "MIT" — **High**

All 23 `packages/*/package.json` have `"license": "MIT"`, the README has a

### D4 — the README does not mention RaptorRuntime — **Medium**

The "Architecture (monorepo)" table lists 21 packages and omits

JavaScript and TypeScript without Node**. That is ~3,700 lines of TS + ~8,000 lines of Rust,
